# 维修订单四模块化需求澄清稿

> 状态：待业务确认  
> 目的：通过问答明确“建单、检测报价、维修与维修后质检、收费结单”四个模块的真实业务边界、生命周期入口、完成条件、权限、异常流和前后端设计依据。  
> 说明：本文不是最终需求文档。所有标记为“待确认”的内容需要业务确认后，才能进入实施设计。

## 1. 核心改造目标

当前维修订单改造不能只是在订单详情页展示四个状态卡片，而应把每个模块设计成独立业务单元。每个模块至少需要具备：

- 独立模块状态。
- 明确的开始动作。
- 明确的完成动作。
- 当前负责人或处理角色。
- 开始时间、完成时间、操作人。
- 完成前置条件和必填校验。
- 可操作动作列表。
- 不可操作原因。
- 时间线记录。
- 审计记录。
- 异常退回或重开规则。

## 2. 总体流程待确认

建议主流程：

```text
建单待开始
  -> 建单中
  -> 建单已完成
  -> 检测报价待开始
  -> 检测报价中
  -> 待客户确认报价
  -> 客户已确认报价
  -> 维修质检待开始
  -> 维修中
  -> 待维修后质检
  -> 质检通过
  -> 收费待开始
  -> 收费中
  -> 已收款待确认
  -> 收费完成
  -> 订单已完结
```

待确认问题：

1. 每个模块是否都必须有“开始”和“完成”两个动作？
2. 是否只允许一个模块处于“进行中”？
3. 上一模块完成后，下一模块是自动开放，还是需要派工/分配？
4. 模块完成后是否允许修改？如果允许，是否必须走“重开模块”？
5. 订单总状态是否完全由模块状态推导？
6. 是否需要保留现有订单状态字段做兼容展示？

## 3. 模块一：建单

建议模块定位：完成接机、客户与机器基础信息登记，使订单达到可检测状态。

建议状态：

- 待开始
- 建单中
- 已完成
- 已退回
- 已重开

建议动作：

- 开始建单
- 保存建单信息
- 完成建单
- 退回建单
- 重开建单

待确认问题：

1. “创建订单”是否等于“开始建单”？
2. 是否允许草稿单？草稿单是否进入模块流程？
3. 完成建单的必填项有哪些？
4. 是否必须上传接机照片？
5. 是否必须做外观/功能初检？
6. 是否需要客户签字或确认？
7. 建单完成后机器状态应变为：待检测、已接机，还是其他？
8. 建单模块由哪些角色操作？

## 4. 模块二：检测报价

建议模块定位：工程师完成检测，形成报价，并取得客户是否维修的确认。

建议状态：

- 待开始
- 检测中
- 已报价
- 待客户确认
- 客户已确认
- 客户拒修
- 已退回
- 已重开

建议动作：

- 开始检测
- 保存检测结果
- 提交报价
- 客户确认报价
- 客户拒绝报价
- 重新报价
- 完成检测报价模块

待确认问题：

1. “客户确认报价”是否属于检测报价模块的完成条件？
2. 客户拒修后，订单是取消、待取机，还是进入收费检测费？
3. 报价是否支持多版本？是否需要保留历史报价？
4. 报价是否必须包含维修项目明细、配件、人工费、总价？
5. 报价确认是否需要记录确认方式：微信、电话、现场、签字？
6. 报价确认是否需要上传凭证？
7. 重新报价时，是重开检测报价模块，还是生成新报价版本？
8. 检测报价模块由哪些角色操作？

## 5. 模块三：维修与维修后质检

建议模块定位：在客户确认报价后执行维修，并通过维修后质检。

建议状态：

- 待开始
- 维修中
- 维修已完成
- 待质检
- 质检中
- 质检通过
- 质检不通过
- 返修中
- 已退回
- 已重开

建议动作：

- 开始维修
- 保存维修过程
- 完成维修
- 开始质检
- 提交质检结果
- 质检通过并完成模块
- 质检不通过并退回维修
- 重开维修质检模块

待确认问题：

1. 维修和维修后质检是否保留在同一模块内？
2. 质检是否需要独立负责人，不能由维修人自己确认？
3. 维修完成时必须录入哪些内容？
4. 是否必须记录实际使用配件？
5. 是否要与库存扣减联动？
6. 质检通过前是否绝对禁止收费？
7. 质检不通过后，是回到“维修中”，还是生成返修轮次？
8. 是否需要记录每次返修原因、返修人、再次质检结果？
9. 质检通过是否自动开放收费模块？
10. 维修质检模块由哪些角色操作？

## 6. 模块四：收费结单

建议模块定位：登记应收、实收、确认收款，完成订单结单。

建议状态：

- 待开始
- 收费中
- 部分收款
- 已收款待确认
- 收费完成
- 已退回
- 已重开

建议动作：

- 开始收费
- 登记收款
- 登记优惠/抹零
- 登记欠款/挂账
- 财务确认收款
- 完成收费并结单
- 重开收费模块

待确认问题：

1. 收费模块是否必须点击“开始收费”？
2. 登记收款和财务确认是否必须分开？
3. 足额收款后是否自动进入“已收款待确认”？
4. 财务确认后是否自动完结订单？
5. 是否支持部分收款？
6. 是否支持欠款、挂账？
7. 是否支持优惠、抹零？
8. 未足额收款是否允许结单？
9. 是否还需要客户取机/交付确认动作？
10. 收费模块由哪些角色操作？

## 7. 权限与可操作动作

待确认角色：

- 前台/客服
- 检测工程师
- 维修工程师
- 质检人员
- 财务
- 店长/管理员

待确认问题：

1. 每个模块的开始、保存、完成、退回、重开分别由谁操作？
2. 管理员是否可以强制完成或重开任意模块？
3. 财务是否只负责确认收款，不负责登记收款？
4. 质检人员是否必须独立于维修人员？
5. 前端按钮是隐藏无权限动作，还是展示禁用并说明原因？

## 8. 数据模型建议方向

建议不要继续只在 `repair_orders` 上增加几个状态字段。更完整的模块化设计应新增模块实例表，用于表达每个订单下的模块生命周期。

建议新增表：

```text
repair_order_modules
```

建议字段：

- id
- repair_order_id
- module_key
- module_name
- status
- sequence
- owner_role
- owner_user_id
- started_at
- started_by
- completed_at
- completed_by
- reopened_at
- reopened_by
- reopen_count
- blocked_reason
- readonly
- created_at
- updated_at

建议新增动作记录表：

```text
repair_order_module_actions
```

建议字段：

- id
- repair_order_id
- module_id
- module_key
- action_key
- action_name
- from_status
- to_status
- actor_user_id
- actor_name
- payload_json
- reason
- created_at

待确认问题：

1. 是否接受新增模块实例表？
2. 是否需要保留模块动作历史用于审计？
3. 是否需要支持模块重开次数和返修轮次？
4. 旧订单如何初始化四个模块？

## 9. 前端页面建议方向

建议订单详情页展示：

- 顶部流程条。
- 四个模块卡片。
- 当前模块展开显示详细表单。
- 未开放模块显示锁定原因。
- 已完成模块只读展示摘要。
- 可重开模块显示重开入口。
- 所有按钮完全来自后端 `available_actions`。

待确认问题：

1. 四个模块都在同一详情页，还是每个模块进入独立页面？
2. 模块操作使用卡片内表单、右侧抽屉，还是弹窗？
3. 完成模块时是否需要二次确认？
4. 退回/重开是否必须填写原因？
5. 是否需要在顶部显示当前卡点和下一步负责人？
