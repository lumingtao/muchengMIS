# 维修订单四模块化开发可行性与实施拆分文档

> 状态：开发规划草案  
> 依据：`docs/repair-order-module-requirements.md` V1.2  
> 生成日期：2026-06-13  
> 视角：产品经理 + 研发实施拆分

## 1. 结论摘要

维修订单四模块化改造具备实施可行性，但不适合一次性“大改全量上线”。该需求涉及订单状态机、模块生命周期、权限、财务、库存、审计、历史数据兼容和前端交互，属于业务主流程重构。

建议采用“底层先行、双轨兼容、逐模块替换、可灰度回退”的开发策略：

1. 先新增模块实例和动作日志能力，不立即替换旧流程。
2. 再实现模块状态机和动作校验，使后端成为唯一业务规则来源。
3. 然后逐步接入四个模块：建单、检测报价、维修质检、收费结单。
4. 前端先展示模块只读状态，再开放动作按钮。
5. 历史订单通过初始化脚本补齐模块数据。
6. 旧接口保留一段兼容期，降低切换风险。

## 2. 产品可行性分析

### 2.1 业务价值

该改造可以解决当前维修订单流程中的几个核心问题：

- 订单状态不够细，无法判断当前卡在哪个业务环节。
- 维修完成、收款、财务确认、完结等动作散落，缺少统一入口。
- 缺少明确的模块开始和完成动作，责任人和处理时间不清楚。
- 维修后质检、预收款、欠款挂账、库存扣减等规则容易靠人工记忆执行。
- 后续审计和问题追溯困难。

模块化后，订单从“单个状态字段驱动”升级为“主订单 + 模块实例 + 模块动作日志”驱动。产品上更适合门店协作，也更适合后续扩展。

### 2.2 用户影响

主要影响角色：

- 前台/客服：建单、预收款登记、收款登记。
- 检测工程师：检测、报价、客户确认记录。
- 维修工程师：维修记录、配件使用、完成维修。
- 质检人员：维修后质检、返修判定。
- 财务：最终收费确认、挂账确认、退款确认。
- 店长/管理员：重开模块、超授信审批、异常处理。

用户体验的变化是明显的。旧流程中用户可能直接点散列按钮，新流程要求先进入模块、点击开始、保存草稿、完成模块。短期学习成本会上升，但流程透明度和责任边界会明显改善。

### 2.3 技术可行性

技术上可行，原因：

- 现有 `repair_orders`、`repair_items`、`payments`、`machine_events` 可复用。
- 新增模块实例表和动作日志表可与旧表并存。
- 详情接口可同时返回旧订单字段和新模块字段。
- 前端可渐进式接入 `modules` 和 `available_actions`。

主要挑战：

- 状态机复杂，必须集中封装，不能散落在接口和前端。
- 历史订单初始化需要谨慎，不能破坏现有订单状态。
- 财务和库存动作需要幂等，避免重复确认、重复扣库存。
- 前端必须严格以后端可用动作为准，避免出现“按钮可点但后端拒绝”的体验断层。

### 2.4 上线可行性

建议分阶段上线，不建议一次性覆盖所有维修订单。

推荐上线顺序：

1. 只读模块视图上线。
2. 新建订单启用建单模块。
3. 检测报价模块接入。
4. 维修质检模块接入。
5. 收费结单模块接入。
6. 历史订单批量初始化。
7. 旧散列按钮下线。

## 3. 范围边界

### 3.1 本期必须做

- 新增模块实例表。
- 新增模块动作日志表。
- 后端模块状态机。
- 后端 `available_actions` 计算。
- 四个模块的开始、保存草稿、完成、退回、重开动作。
- 预收款、欠款挂账、财务确认、库存扣减、返修配件处理。
- 前端四模块展示和动作入口。
- 历史订单初始化脚本。
- 单元测试和端到端业务流测试。

### 3.2 本期不建议做

- 报价多版本。
- 客户取机/交付确认独立模块。
- 复杂审批流引擎。
- 移动端专门重构。
- 自动派工算法。
- 财务对账报表大改。

这些能力可以预留字段和接口扩展点，但不作为第一期交付范围。

## 4. 核心设计原则

1. 后端是流程规则唯一来源。
2. 前端只渲染后端返回的可用动作。
3. 每个模块动作必须幂等。
4. 每次状态变化必须写动作日志。
5. 财务确认、库存扣减、订单完结必须可追溯。
6. 新旧流程需要兼容一段时间。
7. 开发单元要小，每个单元都能独立测试。
8. 任何不可逆动作都必须二次确认。

## 5. 最小开发单元拆分

### 5.1 基础设施层

#### DEV-001 新增模块实例表

目标：新增 `repair_order_modules`。

交付内容：

- 数据表结构。
- 唯一约束：`repair_order_id + module_key`。
- 基础 CRUD 辅助方法。
- 初始化四个模块的函数。

验收：

- 新订单可生成四个模块实例。
- 重复初始化不会生成重复模块。
- 可按订单 ID 查询模块列表。

#### DEV-002 新增模块动作日志表

目标：新增 `repair_order_module_actions`。

交付内容：

- 数据表结构。
- 动作写入函数。
- `payload_json` 保存动作快照。
- 退回、重开、审批、驳回时 reason 必填。

验收：

- 每次模块动作都有日志。
- 日志包含 from_status、to_status、actor、payload、reason。
- 日志查询按时间倒序稳定返回。

#### DEV-003 模块状态常量与动作常量

目标：统一定义模块 key、状态、动作。

交付内容：

- `create`、`quote`、`repair_qc`、`payment`。
- 各模块状态枚举。
- 各模块动作枚举。
- 状态文案映射。

验收：

- 后端和前端文案可复用同一套 key。
- 测试覆盖非法 module/action。

### 5.2 状态机层

#### DEV-004 模块状态机核心

目标：实现纯函数状态机。

交付内容：

- 输入：当前模块、订单上下文、动作、用户角色、payload。
- 输出：是否允许、目标状态、错误原因、衍生动作。
- 不直接写数据库。

验收：

- 建单未完成不能检测。
- 客户未确认报价不能维修。
- 维修未完成不能质检。
- 质检未通过不能最终收费结单。
- 预收款不改变主流程。

#### DEV-005 可用动作计算

目标：生成 `available_actions`。

交付内容：

- 按订单状态、模块状态、角色、门店权限计算动作。
- 返回不可操作原因。
- 支持前端按钮渲染。

验收：

- 无权限用户无对应动作。
- 锁定模块返回锁定原因。
- 店长可重开本门店订单。
- 管理员可重开全部订单。

#### DEV-006 模块动作执行器

目标：统一执行模块动作。

交付内容：

- 校验动作。
- 校验权限。
- 调用状态机。
- 写模块状态。
- 写动作日志。
- 写时间线。
- 返回最新工作流。

验收：

- 任意动作失败不产生半写入。
- 重复提交不会重复扣库存或重复完结。
- 错误信息可给前端直接展示。

### 5.3 建单模块

#### DEV-007 建单模块初始化

目标：新订单创建后初始化建单模块。

交付内容：

- 新订单默认四模块实例。
- 建单为待开始，后续模块锁定。
- 兼容旧建单入口。

验收：

- 新订单详情返回四个模块。
- 只有建单模块可开始。

#### DEV-008 建单开始与负责人

目标：实现开始建单。

交付内容：

- 点击开始后记录 started_by、started_at、owner_user_id。
- 默认谁开始谁负责。
- 店长/管理员可重新分配负责人。

验收：

- 开始后状态变建单中。
- 再次开始被拒绝或幂等返回当前状态。

#### DEV-009 建单草稿保存

目标：保存建单过程数据。

交付内容：

- 保存客户、机器、故障、接机、外观、配件。
- 不强制照片。
- 草稿不推进流程。

验收：

- 可多次保存。
- 保存不开放检测报价。

#### DEV-010 建单完成

目标：完成建单并开放检测报价。

交付内容：

- 必填校验。
- 二次确认。
- 机器状态建议变为待检测。
- 检测报价模块解除锁定。

验收：

- 必填缺失不能完成。
- 完成后检测报价可开始。
- 写动作日志和时间线。

#### DEV-011 建单后预收款入口

目标：建单完成后允许登记预收款。

交付内容：

- 订单顶部财务区入口。
- 建单模块快捷入口。
- 可多次登记，生成独立收款记录。

验收：

- 建单未完成不能登记预收款。
- 预收款不启动收费结单模块。

### 5.4 检测报价模块

#### DEV-012 开始检测

目标：建单完成后开始检测报价。

交付内容：

- 记录检测负责人和开始时间。
- 状态变检测中。

验收：

- 建单未完成不能开始。
- 检测开始后建单模块只读。

#### DEV-013 保存检测报价草稿

目标：保存检测结果和报价明细。

交付内容：

- 检测结果。
- 故障原因。
- 维修方案。
- 维修项目明细。
- 配件费用、人工费、总报价。

验收：

- 草稿可多次保存。
- 未提交报价不允许客户确认。

#### DEV-014 提交报价

目标：提交报价进入待客户确认。

交付内容：

- 报价完整性校验。
- 状态变待客户确认。

验收：

- 缺少明细不能提交。
- 提交后可执行客户确认或重新报价。

#### DEV-015 客户确认报价

目标：客户确认后完成检测报价模块。

交付内容：

- 记录确认方式、时间、凭证。
- 状态变客户已确认。
- 维修质检模块开放。

验收：

- 未提交报价不能确认。
- 确认后维修可开始。

#### DEV-016 报价修改审计

目标：报价不做多版本，但保留修改审计。

交付内容：

- 修改前后总金额。
- 修改前后项目明细。
- 修改原因。
- 操作人。

验收：

- 每次修改都有审计记录。
- 审计摘要可在前端查看。

### 5.5 维修与质检模块

#### DEV-017 开始维修

目标：客户确认报价后开始维修。

交付内容：

- 记录维修负责人。
- 状态变维修中。

验收：

- 未确认报价不能维修。
- 开始后检测报价模块只读。

#### DEV-018 保存维修草稿

目标：保存维修记录和使用配件。

交付内容：

- 维修备注。
- 实际维修项目。
- 使用配件草稿。
- 照片选填。

验收：

- 草稿保存不扣库存。
- 可多次修改使用配件。

#### DEV-019 完成维修并扣减库存

目标：完成维修时扣减库存。

交付内容：

- 检查配件库存。
- 库存不足禁止完成维修。
- 成功后写库存流水。
- 状态进入待质检。

验收：

- 库存不足阻断完成维修。
- 成功完成只扣一次库存。
- 写模块动作日志。

#### DEV-020 开始质检

目标：维修完成后开始质检。

交付内容：

- 记录质检人。
- 质检人可与维修人相同。
- 状态变质检中。

验收：

- 维修未完成不能开始质检。
- 质检开始后维修记录只读，除非返修。

#### DEV-021 质检通过

目标：质检通过后完成维修质检模块。

交付内容：

- 记录质检项目和结果。
- 状态变质检通过。
- 开放最终收费结单。

验收：

- 质检通过前收费结单不可开始。
- 通过后收费结单可开始。

#### DEV-022 质检不通过与返修

目标：质检不通过后进入返修。

交付内容：

- 记录不通过原因。
- 记录返修轮次。
- 支持追加、退回、换件。
- 旧配件状态由操作人选择：可用、待检、报废。

验收：

- 质检不通过不能收费结单。
- 返修配件变动写库存流水。
- 再次完成维修仍检查库存。

### 5.6 收费结单模块

#### DEV-023 开始收费结单

目标：质检通过后开始最终收费结单。

交付内容：

- 状态变收费中。
- 汇总应收、预收、实收、欠款。

验收：

- 质检未通过不能开始。
- 已预收金额正确带入。

#### DEV-024 登记最终收款

目标：登记最终收款记录。

交付内容：

- 支付方式。
- 实收金额。
- 优惠和抹零。
- 预收款抵扣。

验收：

- 可计算剩余应收。
- 财务确认前订单不完结。

#### DEV-025 欠款挂账

目标：同行客户和企业客户可挂账。

交付内容：

- 按客户档案类型判断。
- 账期。
- 授信额度。
- 审批人。
- 超授信允许审批后挂账。

验收：

- 普通客户不能挂账。
- 挂账缺少审批人不能提交。
- 超授信必须有审批理由。

#### DEV-026 财务确认

目标：财务确认收款或挂账结果。

交付内容：

- 确认通过。
- 驳回并填写原因。
- 确认后模块收费完成。

验收：

- 财务未确认不能完结。
- 驳回后回到收费中。
- 确认通过后订单完结、机器已结单。

#### DEV-027 预收款退款

目标：支持预收款退款。

交付内容：

- 前台发起退款申请。
- 财务确认退款。
- 订单进入最终收费结单后，退款必须重开收费模块。

验收：

- 退款有日志。
- 财务未确认退款不生效。

### 5.7 退回、重开、复核

#### DEV-028 模块退回

目标：允许后续模块退回前序模块。

交付内容：

- 退回原因必填。
- 后续已完成模块锁定待复核。
- 当前流程暂停。

验收：

- 退回后不可继续后续动作。
- 后续模块显示锁定待复核原因。

#### DEV-029 后续模块复核

目标：前序修改后复核后续模块。

交付内容：

- 确认有效。
- 复核不通过则重开对应模块。

验收：

- 确认有效后恢复完成态。
- 复核不通过进入重开流程。

#### DEV-030 店长重开模块

目标：店长可重开本门店模块。

交付内容：

- 重开原因必填。
- 店长仅本门店。
- 管理员全部订单。
- 不走审批流。

验收：

- 非本门店店长不能重开。
- 重开写动作日志。

### 5.8 前端实施单元

#### DEV-031 模块流程只读展示

目标：先展示四模块状态，不开放操作。

交付内容：

- 顶部流程条。
- 四个模块卡片。
- 状态、负责人、时间、锁定原因。

验收：

- 旧订单和新订单均能展示。
- 空模块数据有兜底状态。

#### DEV-032 可用动作按钮渲染

目标：按后端 `available_actions` 展示按钮。

交付内容：

- 按钮来自后端。
- 无权限按钮隐藏或禁用并说明。
- 二次确认弹窗。

验收：

- 前端不硬编码业务条件。
- 动作成功后刷新工作流。

#### DEV-033 建单模块表单

目标：建单模块可编辑。

交付内容：

- 开始建单。
- 保存草稿。
- 完成建单。
- 预收款快捷入口。

验收：

- 必填错误可见。
- 完成后模块只读。

#### DEV-034 检测报价模块表单

目标：检测报价模块可编辑。

交付内容：

- 检测草稿。
- 报价明细。
- 客户确认。
- 报价修改审计摘要。

验收：

- 报价总额计算正确。
- 客户确认后只读。

#### DEV-035 维修质检模块表单

目标：维修、配件、质检、返修操作。

交付内容：

- 维修草稿。
- 使用配件。
- 完成维修。
- 质检结果。
- 返修配件处理。

验收：

- 库存不足错误能展示处理入口。
- 质检不通过后返修入口可用。

#### DEV-036 收费结单模块表单

目标：最终收款、挂账、财务确认。

交付内容：

- 应收汇总。
- 预收款抵扣。
- 收款记录。
- 挂账字段。
- 财务确认。

验收：

- 财务确认后订单完结。
- 普通客户不能挂账。

#### DEV-037 顶部财务区

目标：支持预收款和财务摘要。

交付内容：

- 预收款合计。

## 7. 调试与冗余设计

### 7.1 功能开关

建议增加以下开关：

- 是否启用模块化详情页。
- 是否启用模块动作接口。
- 是否启用库存扣减。
- 是否启用财务确认完结。
- 是否允许旧接口转发新模块动作。

用途：

- 灰度上线。
- 快速回退。
- 定位问题时隔离模块。

### 7.2 幂等键

关键动作建议支持幂等键：

- 完成维修。
- 扣减库存。
- 财务确认。
- 订单完结。
- 退款确认。

避免：

- 网络重试导致重复扣库存。
- 重复财务确认。
- 重复订单完结。

### 7.3 审计快照

动作日志中的 `payload_json` 应保存关键快照：

- 报价修改前后金额和明细。
- 配件扣减明细。
- 挂账审批信息。
- 财务确认信息。
- 退回和重开原因。

用途：

- 排查问题。
- 复盘业务争议。
- 支撑后续报表。

### 7.4 兼容字段

短期保留 `repair_orders.status` 作为聚合状态。

建议：

- 列表仍使用聚合状态。
- 详情使用模块状态。
- 每次模块完成后同步更新聚合状态。

避免：

- 一次性改造列表、统计、报表导致风险扩大。

### 7.5 调试页面

建议开发内部调试视图：

- 查看订单四模块原始状态。
- 查看可用动作计算结果。
- 查看最近动作日志。
- 查看锁定原因。
- 查看状态机拒绝原因。

该页面只给管理员或开发调试使用。

## 8. 主要风险与缓解方案

| 风险 | 等级 | 表现 | 缓解 |
| --- | --- | --- | --- |
| 状态机过复杂 | 高 | 动作互相冲突 | 状态机纯函数 + 单元测试 |
| 历史订单初始化错误 | 高 | 旧订单卡死 | 初始化脚本先 dry-run，输出报告 |
| 重复扣库存 | 高 | 库存异常 | 幂等键 + 库存流水唯一关联 |
| 财务重复确认 | 高 | 收款重复入账 | 财务确认幂等 + 状态锁 |
| 前端按钮和后端规则不一致 | 中 | 用户点击失败 | 前端只用 available_actions |
| 用户学习成本 | 中 | 不知道下一步 | 顶部下一步提示和锁定原因 |
| 旧接口调用混乱 | 中 | 新旧状态不一致 | 旧接口转发新动作并记录日志 |
| 模块退回影响后续模块 | 中 | 后续结论失效 | 后续模块锁定待复核 |

## 10. 最小可交付版本建议

如果需要压缩第一版范围，建议最小可交付版本为：

1. 新增模块实例表和动作表。
2. 状态机和 available_actions。
3. 建单、检测报价、维修质检、收费结单四模块主流程。
4. 预收款登记。
5. 完成维修时库存扣减。
6. 财务确认后订单完结。
7. 前端四模块卡片和按钮。

暂缓：

- 预收款退款。
- 超授信审批细节。
- 返修配件复杂状态。
- 后续模块逐个复核。
- 旧接口转发。

但即使暂缓，也要在数据模型中预留字段，避免后续返工。

## 12. 产品验收口径

产品验收不应只看页面是否出现四个模块，而应按以下口径验收：

1. 每个模块是否有独立状态。
2. 每个模块是否有开始和完成动作。
3. 每个动作是否记录操作人和时间。
4. 每个动作是否写入审计日志。
5. 前端按钮是否全部来自后端。
6. 上一模块未完成时下一模块是否锁定。
7. 预收款是否不破坏主流程。
8. 质检未通过是否不能最终收费结单。
9. 财务未确认是否不能完结订单。
10. 完成维修是否正确扣减库存。
11. 异常退回后后续模块是否锁定待复核。
12. 完结订单是否只读。
