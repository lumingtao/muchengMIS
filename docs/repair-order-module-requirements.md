# 维修订单四模块化改造需求文档 V1.2

> 状态：已按第四轮业务确认修订  
> 分支：codex/repair-order-modules  
> 生成日期：2026-06-13  
> 关联澄清稿：`docs/repair-order-module-requirements-questionnaire.md`

## 1. 背景

当前维修订单流程已经尝试拆分为“建单、检测报价、维修与维修后质检、收费结单”四个板块，但现有实现仍偏向页面展示层：模块只是订单状态的摘要卡片，缺少真正的模块生命周期、开始入口、结束入口、负责人、前置校验、退回重开、审计记录和明确交接规则。

本次需求目标是把四个板块改造为订单下的四个独立业务模块。每个模块既是前端上的独立操作区域，也是后端上的独立流程单元。

## 2. 改造目标

1. 维修订单拆分为四个固定模块：
   - 建单
   - 检测报价
   - 维修与维修后质检
   - 收费结单
2. 每个模块具备独立生命周期：
   - 待开始
   - 进行中
   - 待确认或待质检等业务中间态
   - 已完成
   - 已退回
   - 已重开
3. 每个模块都必须提供明确入口：
   - 开始模块
   - 保存模块过程信息
   - 完成模块
   - 退回模块
   - 重开模块
4. 上一个模块完成后，下一个模块才允许开始。
5. 维修后质检未通过前，不允许最终收费结单；但允许在前序模块中登记预收款。
6. 收费完成并经财务确认后，订单进入已完结；同行客户和企业客户允许欠款挂账结单。
7. 所有模块动作必须写入订单时间线和审计日志。
8. 前端所有操作按钮必须来自后端 `available_actions`，不能自行判断展示关键业务动作。

## 3. 核心术语

| 术语 | 定义 |
| --- | --- |
| 订单 | 一次客户维修业务的主记录。 |
| 模块 | 订单下的固定业务阶段，拥有独立状态、动作、负责人和审计记录。 |
| 开始模块 | 代表该模块被正式接手处理，记录开始人和开始时间。 |
| 完成模块 | 代表该模块达到业务交付条件，记录完成人和完成时间，并开放下一模块。 |
| 退回模块 | 当前模块不满足完成条件或被后续环节驳回，需要回到指定状态重新处理。 |
| 重开模块 | 已完成模块因业务修正被重新打开，必须记录原因和操作人。 |
| 可用动作 | 后端根据订单、模块、角色、权限和状态计算出的当前用户可执行动作。 |

## 4. 总流程

建议主流程如下：

```text
建单待开始
  -> 建单中
  -> 建单已完成
  -> 检测报价待开始
  -> 检测中
  -> 已报价
  -> 待客户确认报价
  -> 客户已确认报价
  -> 维修质检待开始
  -> 维修中
  -> 维修已完成
  -> 待维修后质检
  -> 质检中
  -> 质检通过
  -> 收费结单待开始
  -> 收费中
  -> 已收款待确认
  -> 收费完成
  -> 订单已完结
```

硬性规则：

1. 建单未完成，不允许开始检测报价。
2. 客户未确认报价，不允许开始维修。
3. 维修未完成，不允许开始维修后质检。
4. 维修后质检不通过，不允许完成最终收费结单。
5. 维修后质检通过，才允许开始最终收费结单。
6. 收费未完成或财务未确认，不允许订单完结。
7. 订单完结后，所有模块默认只读；只有管理员可发起重开。
8. 预收款登记不等于开始收费结单模块，不改变四模块主流程顺序。
9. 同行客户和企业客户可在财务确认后以欠款或挂账方式完成收费结单。

## 5. 模块一：建单

### 5.1 模块定位

建单模块负责完成客户、机器、故障、接机、初检等基础信息登记，使订单达到可检测状态。

### 5.2 状态

| 状态 | 说明 |
| --- | --- |
| 待开始 | 订单已创建但建单未正式开始，或草稿刚生成。 |
| 建单中 | 前台或客服正在录入建单信息。 |
| 已完成 | 建单信息满足检测报价前置条件。 |
| 已退回 | 后续环节发现建单信息不完整，退回补充。 |
| 已重开 | 已完成建单被重新打开修改。 |

### 5.3 动作

| 动作 | 触发条件 | 结果 |
| --- | --- | --- |
| 开始建单 | 订单存在且建单未开始 | 模块状态变为建单中，记录开始人和时间。 |
| 保存建单信息 | 模块处于建单中或已重开 | 保存客户、机器、故障、附件等信息。 |
| 完成建单 | 必填项通过校验 | 模块状态变为已完成，开放检测报价模块。 |
| 退回建单 | 后续模块发现基础信息有误 | 模块状态变为已退回，订单暂停向后流转。 |
| 重开建单 | 已完成后需要修正 | 模块状态变为已重开，必须填写原因。 |

### 5.4 完成条件

默认必填项：

- 客户姓名。
- 客户手机号。
- 机器品牌/型号。
- 机器序列号或 IMEI，若无则必须填写无序列号原因。
- 故障描述。
- 接机门店。
- 接机人。
- 接机时间。
- 外观初检结果。
- 随机配件记录。

待业务确认项：

- 是否必须客户签字。
- 是否允许草稿单不进入模块流程。
- 建单完成后机器状态名称：建议为 `待检测`。

## 6. 模块二：检测报价

### 6.1 模块定位

检测报价模块负责接收已建单机器，完成故障检测、维修方案、报价明细，并取得客户确认。

### 6.2 状态

| 状态 | 说明 |
| --- | --- |
| 待开始 | 建单已完成，检测报价未开始。 |
| 检测中 | 工程师已开始检测。 |
| 已报价 | 已提交报价明细。 |
| 待客户确认 | 报价已通知客户，等待客户确认。 |
| 客户已确认 | 客户同意维修报价。 |
| 客户拒修 | 客户不同意维修。 |
| 已退回 | 因信息或报价问题退回修改。 |
| 已重开 | 已完成报价被重新打开。 |

### 6.3 动作

| 动作 | 触发条件 | 结果 |
| --- | --- | --- |
| 开始检测 | 建单模块已完成 | 状态变为检测中。 |
| 保存检测结果 | 检测中或已重开 | 保存检测信息。 |
| 提交报价 | 检测结果和报价明细完整 | 状态变为已报价或待客户确认。 |
| 客户确认报价 | 报价已提交 | 状态变为客户已确认，开放维修质检模块。 |
| 客户拒绝报价 | 报价已提交 | 状态变为客户拒修，后续进入拒修处理流程。 |
| 重新报价 | 客户要求调整或工程师修正 | 重开当前报价并覆盖当前报价内容，动作历史进入审计。 |
| 完成检测报价模块 | 客户已确认报价 | 模块完成，开放下一模块。 |

### 6.4 完成条件

默认必填项：

- 检测结果。
- 故障原因。
- 维修方案。
- 报价项目明细。
- 配件费用。
- 人工费用。
- 总报价。
- 预计交付时间。
- 客户确认结果。
- 客户确认方式。
- 确认时间。

已确认规则：

- 报价不做多版本管理。
- 重新报价以当前报价修订为准，历史变化通过模块动作审计追踪。
- 报价修改必须在审计日志中记录修改前金额、修改后金额、修改原因和操作人。

待业务确认项：

- 客户确认是否需要上传微信/签字/电话记录凭证。
- 客户拒修是否需要收取检测费。
- 客户拒修后订单状态：建议为 `客户拒修待取机`。

## 7. 模块三：维修与维修后质检

### 7.1 模块定位

维修与维修后质检模块负责在客户确认报价后执行维修，并完成维修后的质量检查。质检通过是最终收费结单和订单完结的前置条件；预收款登记不受该条件限制。

### 7.2 状态

| 状态 | 说明 |
| --- | --- |
| 待开始 | 客户已确认报价，维修未开始。 |
| 维修中 | 维修工程师已开始维修。 |
| 维修已完成 | 维修工程师提交维修完成。 |
| 待质检 | 等待质检人员检查。 |
| 质检中 | 质检人员正在检查。 |
| 质检通过 | 维修后质检合格，开放收费。 |
| 质检不通过 | 质检失败，不允许收费。 |
| 返修中 | 质检不通过后退回维修。 |
| 已退回 | 因报价、配件或信息问题退回前序模块。 |
| 已重开 | 已通过质检后因异常重新打开。 |

### 7.3 动作

| 动作 | 触发条件 | 结果 |
| --- | --- | --- |
| 开始维修 | 客户已确认报价 | 状态变为维修中。 |
| 保存维修过程 | 维修中或返修中 | 保存维修记录、配件使用、照片等。 |
| 完成维修 | 维修记录完整 | 状态变为维修已完成，并进入待质检。 |
| 开始质检 | 维修已完成 | 状态变为质检中。 |
| 提交质检结果 | 质检中 | 保存质检项目和结果。 |
| 质检通过并完成模块 | 质检结果合格 | 状态变为质检通过，开放收费模块。 |
| 质检不通过并退回维修 | 质检结果不合格 | 状态变为返修中，记录返修轮次。 |
| 重开维修质检模块 | 已通过后发现问题 | 重开模块，必须填写原因。 |

### 7.4 完成条件

默认必填项：

- 实际维修项目。
- 维修工程师。
- 维修完成时间。
- 实际使用配件。
- 维修备注。
- 质检人员。
- 质检项目。
- 质检结果。
- 质检时间。

硬性规则：

- 质检不通过时，最终收费结单必须锁定。
- 质检不通过后必须回到维修或返修状态。
- 每次质检不通过都要记录原因和返修轮次。
- 质检人员可以与维修人员相同，系统不做强制隔离，但必须记录质检人。

已确认规则：

- 质检人员不强制要求不同于维修人员。
- 接机、维修、质检照片不作为必传项。
- 维修使用配件需要联动库存扣减。
- 配件库存扣减发生在完成维修时。
- 质检不通过返修后，已扣减配件支持追加、退回、换件，并进入库存流水和审计记录。

## 8. 模块四：收费结单

### 8.1 模块定位

收费结单模块负责登记维修应收、实收、优惠、欠款、挂账、支付方式，并由财务确认后完成订单。系统支持前序模块中的预收款登记，但预收款不代表收费结单模块已经开始。

### 8.2 状态

| 状态 | 说明 |
| --- | --- |
| 待开始 | 维修后质检通过，收费未开始。 |
| 收费中 | 前台或收银正在处理收费。 |
| 部分收款 | 已登记部分款项，未足额。 |
| 已预收 | 前序模块已登记预收款，但尚未进入最终收费结单。 |
| 已收款待确认 | 已登记足额收款，等待财务确认。 |
| 挂账待确认 | 同行客户或企业客户申请欠款挂账，等待财务确认。 |
| 收费完成 | 财务已确认收款。 |
| 已退回 | 财务驳回收款记录。 |
| 已重开 | 结单后因退款、差错等重开。 |

### 8.3 动作

| 动作 | 触发条件 | 结果 |
| --- | --- | --- |
| 开始收费 | 质检通过 | 状态变为收费中。 |
| 登记预收款 | 建单完成后，客户提前支付 | 记录预收款，不启动最终收费结单模块。 |
| 登记收款 | 收费中或部分收款 | 新增收款记录。 |
| 登记优惠/抹零 | 收费中 | 影响应收金额。 |
| 登记欠款/挂账 | 收费中，且客户为同行客户或企业客户 | 标记欠款或挂账金额，进入挂账待确认。 |
| 财务确认收款 | 已收款待确认或挂账待确认 | 状态变为收费完成。 |
| 完成收费并结单 | 财务确认且满足结单条件 | 订单变为已完结，机器变为已结单。 |
| 重开收费模块 | 已完成后发生退款或差错 | 模块重开并记录原因。 |

### 8.4 完成条件

默认必填项：

- 应收金额。
- 实收金额。
- 支付方式。
- 收款人。
- 收款时间。
- 财务确认人。
- 财务确认时间。

硬性规则：

- 质检通过前不允许开始最终收费结单。
- 建单完成后允许登记预收款，但不允许订单完结。
- 预收款最终在收费结单模块中统一提交财务确认。
- 未财务确认前不允许订单完结。
- 收费完成后订单状态自动变为 `已完结`。
- 收费完成后机器状态自动变为 `已结单`。
- 同行客户和企业客户允许欠款或挂账结单，必须经过财务确认。
- 同行客户和企业客户通过客户档案类型识别。
- 欠款挂账必须记录账期、授信额度和审批人。

已确认规则：

- 登记收款和财务确认必须拆成两个动作。
- 预收款不单独财务确认，在最终收费结单时统一确认。
- 默认允许同行客户和企业客户欠款挂账结单。
- 同行客户和企业客户通过客户档案类型识别。
- 欠款挂账必须设置账期、授信额度和审批人。
- 不需要客户取机/交付确认动作。
- 收费完成并财务确认后，订单自动完结、机器自动已结单。

## 9. 权限矩阵

建议默认权限：

| 角色 | 建单 | 检测报价 | 维修 | 质检 | 收费登记 | 财务确认 | 退回/重开 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 前台/客服 | 开始、保存、完成 | 查看 | 查看 | 查看 | 开始、登记 | 无 | 申请 |
| 检测工程师 | 查看 | 开始、保存、提交报价 | 查看 | 查看 | 查看 | 无 | 申请 |
| 维修工程师 | 查看 | 查看 | 开始、保存、完成维修 | 查看 | 查看 | 无 | 申请 |
| 质检人员 | 查看 | 查看 | 查看维修记录 | 开始、提交、通过/不通过 | 查看 | 无 | 申请 |
| 财务 | 查看 | 查看 | 查看 | 查看 | 查看 | 确认/驳回 | 申请 |
| 店长/管理员 | 全部 | 全部 | 全部 | 全部 | 全部 | 全部 | 审批、强制重开 |

已确认规则：

- 质检人员不强制要求和维修人员不同。
- 管理员不允许强制跳过模块，只允许重开或审批异常。
- 财务确认必须作为独立动作执行。

## 10. 数据模型设计

### 10.1 新增模块实例表

建议新增 `repair_order_modules`，用于记录每个订单下四个模块的当前生命周期。

字段建议：

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| repair_order_id | 维修订单 ID |
| module_key | 模块编码：create、quote、repair_qc、payment |
| module_name | 模块名称 |
| sequence | 模块顺序 |
| status | 模块状态 |
| owner_role | 当前建议处理角色 |
| owner_user_id | 当前负责人 |
| started_at | 开始时间 |
| started_by | 开始人 |
| completed_at | 完成时间 |
| completed_by | 完成人 |
| reopened_at | 最近重开时间 |
| reopened_by | 最近重开人 |
| reopen_count | 重开次数 |
| blocked_reason | 锁定或不可操作原因 |
| readonly | 是否只读 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

### 10.2 新增模块动作表

建议新增 `repair_order_module_actions`，用于记录模块动作历史和审计。

字段建议：

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| repair_order_id | 维修订单 ID |
| module_id | 模块实例 ID |
| module_key | 模块编码 |
| action_key | 动作编码 |
| action_name | 动作名称 |
| from_status | 操作前状态 |
| to_status | 操作后状态 |
| actor_user_id | 操作人 ID |
| actor_name | 操作人名称 |
| payload_json | 操作提交数据 |
| reason | 原因，退回/重开/驳回时必填 |
| created_at | 操作时间 |

### 10.3 兼容现有表

保留并复用：

- `repair_orders`
- `repair_items`
- `payments`
- `machine_events`

现有订单状态可继续作为聚合状态，用于列表筛选和兼容旧接口；模块真实状态以 `repair_order_modules` 为准。

## 11. 接口设计

### 11.1 详情接口

```http
GET /api/repair-orders/{repair_order_id}/module-workflow
```

返回建议：

```json
{
  "order": {},
  "modules": [],
  "current_module": "repair_qc",
  "available_actions": [],
  "timeline": [],
  "audit_logs": []
}
```

### 11.2 模块动作接口


## 13. 异常与回退规则

1. 建单信息错误：
   - 检测报价模块可退回建单。
   - 退回后检测报价模块暂停。
2. 报价错误：
   - 维修前可重新报价。
   - 已维修后原则上不允许修改报价，只能走管理员审批。
3. 客户拒修：
   - 订单进入拒修待处理。
   - 待确认是否收取检测费。
4. 质检不通过：
   - 禁止最终收费结单。
   - 已登记的预收款保留为财务记录，不允许用于完结订单。
   - 自动退回维修或返修状态。
   - 记录返修轮次。
5. 收款被财务驳回：
   - 收费模块回到收费中。
   - 必须记录驳回原因。
6. 已完结订单重开：
   - 仅管理员可操作。
   - 必须填写原因。
   - 必须写入审计日志。
7. 欠款挂账：
   - 仅同行客户和企业客户可使用。
   - 同行客户和企业客户通过客户档案类型识别。
   - 必须记录账期、授信额度和审批人。
   - 必须经过财务确认。
   - 财务确认后可完成收费结单并完结订单。
8. 预收款：
   - 建单完成后即可登记。
   - 不启动收费结单模块。
   - 在最终收费结单时统一财务确认。
   - 不允许绕过维修后质检和订单完结规则。
9. 配件库存：
   - 完成维修时扣减实际使用配件库存。
   - 质检不通过返修后，支持追加配件、退回配件、换件。
   - 所有配件变更必须写入库存流水和模块动作审计。
10. 报价修订：
   - 报价不做多版本。
   - 每次报价修改必须记录修改前金额、修改后金额、修改原因和操作人。

## 14. 历史数据兼容

上线时需要为旧维修订单初始化四个模块。

建议规则：

1. 已完结订单：
   - 四个模块均初始化为已完成。
   - 模块只读。
2. 维修中订单：
   - 建单、检测报价初始化为已完成。
   - 维修质检根据当前状态初始化为维修中或待质检。
   - 收费模块初始化为待开始。
3. 待收费订单：
   - 建单、检测报价、维修质检初始化为已完成或质检通过。
   - 收费模块初始化为待开始或收费中。
4. 新订单：
   - 只初始化建单模块为待开始。
   - 后续模块为锁定状态。

## 15. 测试验收标准

### 15.1 后端

- 建单未完成不能开始检测报价。
- 检测报价未客户确认不能开始维修。
- 维修未完成不能开始质检。
- 质检不通过不能开始最终收费结单。
- 质检不通过不能完成最终收费结单。
- 质检不通过后回到返修或维修中。
- 质检通过后开放最终收费结单模块。
- 预收款不能完结订单。
- 预收款建单完成后可登记，并在最终收费结单时统一财务确认。
- 部分收款不能完结订单，除非该客户为允许挂账的同行客户或企业客户且财务确认挂账。
- 财务未确认不能完结订单。
- 足额收款且财务确认后订单完结。
- 同行客户或企业客户欠款挂账经财务确认后可完结订单。
- 欠款挂账必须记录账期、授信额度和审批人。
- 订单完结后机器状态变为已结单。
- 完成维修时扣减实际使用配件库存。
- 返修配件追加、退回、换件必须生成库存流水。
- 报价修改必须写入修改前后金额。
- 每个模块动作写入时间线。
- 每个模块动作写入审计日志。
- 重开模块必须记录原因。
- 权限不足时动作不可执行。

### 15.2 前端

- 四个模块按后端状态启用或锁定。
- 前端只按后端 `available_actions` 渲染按钮。
- 每个模块都有开始入口和完成入口。
- 当前模块可编辑，未开放模块不可编辑。
- 已完成模块默认只读。
- 质检通过前最终收费结单模块不可操作。
- 建单完成后允许展示预收款登记入口；质检通过前最终收费结单入口不可操作。
- 欠款挂账表单必须展示账期、授信额度和审批人字段。
- 财务确认前订单不可完结。
- 完结订单所有模块只读。
- 退回/重开时展示原因输入。

## 16. 第一轮业务确认结论

1. 四个模块确认作为订单下独立任务，而不仅是页面区块。
2. 每个模块确认必须有开始和完成动作。
3. 同一时间只允许一个模块处于进行中。
4. 确认新增 `repair_order_modules` 和 `repair_order_module_actions` 两张表。
5. 客户确认报价属于检测报价模块的完成条件。
6. 质检人员不强制要求不同于维修人员。
7. 质检通过不是收费相关动作的唯一入口，因为存在预收费；但质检通过仍是最终收费结单和订单完结的前置条件。
8. 登记收款和财务确认必须拆成两个动作。
9. 同行客户和企业客户允许欠款挂账结单。
10. 收费完成并财务确认后，订单自动完结、机器自动已结单。
11. 不需要客户取机/交付确认动作。
12. 报价不需要多版本。
13. 维修使用配件需要联动库存扣减。
14. 接机、维修、质检照片不强制必传。
15. 管理员不允许跳过模块，只能重开或审批异常。

## 17. 第二轮业务确认结论

1. 预收款最早允许在建单完成后登记。
2. 预收款不单独财务确认，在最终收费结单时统一确认。
3. 同行客户和企业客户通过客户档案类型识别。
4. 欠款挂账需要设置账期、授信额度和审批人。
5. 配件库存扣减发生在完成维修时。
6. 质检不通过返修后，已扣减配件支持追加、退回、换件。
7. 报价修改需要记录修改前金额和修改后金额。

## 18. 第三轮待确认问题

1. 建单完成后允许登记预收款，那么预收款入口放在哪个模块中：建单模块内、订单顶部财务区，还是收费结单模块的提前入口？
2. 预收款是否允许多次登记？如果允许，是否每次都生成独立收款记录？
3. 预收款是否允许退款？如果允许，退款由前台发起还是财务发起？
4. 欠款挂账审批人是必须从系统用户中选择，还是允许手填姓名？
5. 授信额度校验是强校验还是提醒：超过授信额度禁止挂账，还是允许审批通过后挂账？
6. 完成维修时扣减库存，如果库存不足，是禁止完成维修，还是允许负库存并提示异常？
7. 返修换件时，旧配件退回库存的状态是什么：可用、待检、报废，还是由操作人选择？
8. 报价修改记录前后金额时，是否还需要记录每个维修项目明细的前后变化？
9. 模块重开是否需要审批流，还是管理员/店长可直接重开？
10. 退回模块时，是只退回当前模块，还是后续已完成模块全部变为锁定待复核？

## 19. 第三轮业务确认结论

1. 预收款入口建议放在订单顶部财务区，同时在建单完成后显示快捷入口。
2. 预收款允许多次登记，每次生成独立收款记录。
3. 预收款允许退款，由前台发起退款申请，财务确认退款。
4. 欠款挂账审批人必须从系统用户中选择。
5. 超过授信额度时，允许审批后挂账。
6. 完成维修时库存不足，禁止完成维修。
7. 返修换件时，旧配件退回库存状态由操作人选择：可用、待检、报废。
8. 报价修改需要记录维修项目明细的前后变化。
9. 店长可直接重开模块，不走审批流。
10. 退回模块时，后续已完成模块全部变为锁定待复核，避免前序变更后后续结论失效。

## 20. 第四轮待确认问题

1. 店长直接重开模块时，是否仍必须填写重开原因？
2. 店长重开模块是否需要限制范围：只能重开本门店订单，还是可重开全部订单？
3. 超授信审批后挂账，审批人是店长、管理员、财务，还是都可以？
4. 超授信审批是否需要记录审批理由和审批时间？
5. 库存不足禁止完成维修时，系统应该提示去哪里处理：采购入库、调拨入库，还是允许修改使用配件？
6. 预收款退款时，如果订单已经进入最终收费结单，是否仍允许退款？
7. 退回模块导致后续模块锁定待复核时，后续模块复核是逐个点击“确认有效”，还是重新走开始/完成动作？
8. 模块完成按钮是否都需要二次确认弹窗？
9. 每个模块是否需要“保存草稿”动作，还是表单自动保存？
10. 模块负责人是手动分配，还是谁点击“开始模块”谁就是负责人？

## 21. 第四轮业务确认结论

1. 店长直接重开模块时仍必须填写重开原因。
2. 店长只能重开本门店订单；管理员可重开全部订单。
3. 超授信审批人建议为店长或管理员，财务只负责确认收款和挂账结果。
4. 超授信审批必须记录审批理由、审批人、审批时间。
5. 库存不足禁止完成维修时，系统提示三个处理入口：采购入库、调拨入库、修改使用配件。
6. 订单进入最终收费结单后，预收款不再单独退款；如需退款，必须重开收费模块。
7. 退回模块导致后续模块锁定待复核时，后续模块逐个点击“确认有效”即可恢复；若复核不通过，则重开对应模块。
8. 所有模块完成按钮都需要二次确认弹窗。
9. 每个模块都提供“保存草稿”动作，不做强制自动保存。
10. 模块负责人默认为谁点击“开始模块”谁负责；店长或管理员可重新分配负责人。

### 23.6 收费结单模块字段

- 应收金额。
- 预收款记录。
- 实收记录。
- 优惠和抹零。
- 欠款挂账信息。
- 财务确认信息。
- 订单完结结果。

## 24. 补充验收用例草案

1. 建单完成后可登记预收款，登记后检测报价模块仍按正常流程开放。
2. 预收款未财务确认时，最终收费结单统一提交财务确认。
3. 普通客户不允许欠款挂账。
4. 同行客户和企业客户允许提交欠款挂账。
5. 超授信挂账必须有审批人和审批理由。
6. 完成维修时库存不足，禁止完成维修。
7. 完成维修成功后生成库存扣减流水。
8. 返修追加、退回、换件均生成库存流水。
9. 报价修改记录修改前后总金额和明细。
10. 店长重开模块必须填写原因。
11. 退回前序模块后，后续模块进入锁定待复核。
12. 锁定待复核模块确认有效后恢复完成态。
13. 模块完成动作必须二次确认。
14. 无权限用户看不到或不能执行模块动作。
