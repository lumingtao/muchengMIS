## BUG 明细

### BUG-20260613-001：订单编号生成格式错误

- 反馈时间：2026-06-13
- 反馈来源：使用反馈
- 影响模块：维修订单/订单编号
- 严重程度：P1 核心流程异常
- 当前状态：已修复待验证
- 问题现象：订单列表中出现 `RO-20`、`RO-13`、`RO-14`、`RO-19`、`RO-18` 等不符合规则的订单编号；截图中也存在符合预期的新格式编号，例如 `R-20260607-001`、`R-20260605-002`。
- 复现步骤：进入订单列表/维修订单列表，查看“订单编号”列。
- 期望结果：订单编号应按照 `R-YYYYMMDD-序号` 格式生成，例如 `R-20260605-001`；同一天订单序号应从 `001` 开始递增并保持三位补零。
- 实际结果：部分订单编号生成或展示为 `RO-数字` 格式，不符合当前业务要求。
- 影响范围：影响订单识别、业务追踪、查询筛选、后续报表和人工对账。
- 初步判断：可能存在旧编号生成逻辑、测试数据生成逻辑或列表展示字段未统一的问题；需检查新增订单、历史导入订单和前端展示是否使用同一编号来源。
- 建议修复方向：统一订单编号生成规则为 `R-YYYYMMDD-001` 格式；新建订单必须使用该规则；如保留历史订单，需要明确是否迁移旧编号或仅修正后续新增订单。
- 验证要点：新建当天第一条订单生成 `R-YYYYMMDD-001`；同一天连续新建订单序号递增；跨日期后序号重新从 `001` 开始；订单列表、详情页、搜索结果和导出报表展示一致。
- 修复说明：新增统一订单编号工具，创建维修单时按 `R-YYYYMMDD-三位序号` 写入；数据库迁移会幂等修正空编号和 `RO-数字` 历史编号；列表和详情兜底展示也已改为新格式。
- 验证结果：后端测试已覆盖新编号格式、同日递增和历史 `RO-数字` 迁移；当前状态等待实际使用验收。
- 备注：用户原始反馈：“订单编号的生成逻辑有问题，按照‘R-20260605-001’的格式生成。”截图路径：`C:/Users/admini/AppData/Local/Temp/codex-clipboard-ecb31e1b-d293-4359-be34-da51c47af85b.png`。

### BUG-20260613-002：分页按钮点击无反应

- 反馈时间：2026-06-13
- 反馈来源：使用反馈
- 影响模块：订单列表/分页
- 严重程度：P2 普通功能异常
- 当前状态：已修复待验证
- 问题现象：列表底部显示分页控件，包括上一页箭头、页码 `1`、`2`、`3`、省略号、`321` 和下一页箭头，但点击翻页按钮没有任何反应。
- 复现步骤：进入订单列表页面，滚动或查看列表底部分页区域，点击页码或左右翻页箭头。
- 期望结果：点击页码应切换到对应页；点击左右箭头应切换到上一页或下一页；当前页状态和列表数据应同步更新。
- 实际结果：点击分页按钮后页面无响应，列表数据和当前页状态没有变化。
- 影响范围：影响用户浏览多页订单、查找历史订单和核对列表数据。
- 初步判断：可能存在分页按钮事件未绑定、分页状态未接入数据加载、前端只渲染了静态分页 UI，或接口分页参数未联动的问题。
- 建议修复方向：为分页控件补齐点击事件和当前页状态管理；切换页码时重新请求或筛选对应页数据；确保按钮禁用态、当前页高亮和数据刷新一致。
- 验证要点：点击 `2`、`3`、末页和左右箭头能正确切换页面；当前页高亮随之变化；列表内容更新；第一页禁用上一页，最后一页禁用下一页；刷新或筛选后分页状态符合预期。
- 修复说明：订单池分页改为真实状态驱动，支持上一页、下一页、动态页码、省略号和筛选后回到第一页；分页摘要显示真实数据区间。
- 验证结果：前端单元测试已覆盖分页页码生成；构建通过；当前状态等待实际点击验收。
- 备注：用户原始反馈：“下方翻页按钮的交互没有做，点击没有任何反应，记录。”截图路径：`C:/Users/admini/AppData/Local/Temp/codex-clipboard-8b1d8053-80aa-4235-971c-0118f1ccf559.png`。

### BUG-20260613-003：未填写字段被自动生成默认值

- 反馈时间：2026-06-13
- 反馈来源：使用反馈
- 影响模块：客户资料/空值处理
- 严重程度：P1 核心流程异常
- 当前状态：已修复待验证
- 问题现象：电话号码未填写时，系统生成并展示默认电话号码，例如截图中的 `138****0000`；用户要求未填写就留空。其他字段也需要按照“未填写就留空”的原则设计。
- 复现步骤：创建或导入未填写电话号码的订单/客户资料，进入订单列表查看客户信息区域。
- 期望结果：电话号码未填写时应保持为空，不自动生成默认号码；其他非必填字段未填写时也应保持为空，不生成虚假默认值。
- 实际结果：未填写电话号码被系统展示为默认号码 `138****0000`。
- 影响范围：影响客户资料真实性、电话联系、订单追踪、对账和后续数据清洗。
- 初步判断：可能存在测试数据兜底逻辑、前端展示 fallback、后端字段默认值、导入脚本默认填充或脱敏展示逻辑误用的问题。
- 建议修复方向：清理电话号码及其他非必填字段的默认值生成逻辑；展示层只对真实已有值做脱敏，不应从空值生成假数据；新增、导入、编辑、列表和详情页统一遵循“未填写就留空”。
- 验证要点：未填写电话号码的新建订单在列表和详情中均为空；已填写电话号码仍正常脱敏展示；其他非必填字段为空时不出现默认文案、默认号码或模拟数据；导入历史数据时不补造缺失字段。
- 修复说明：移除电话号码和客户信息展示层的模拟默认值；脱敏函数只处理真实已有值，表格空电话显示 `-`，详情空值留空。
- 验证结果：前端测试已覆盖空电话不再生成默认号码、真实电话仍正常脱敏；当前状态等待实际数据验收。
- 备注：用户原始反馈：“电话号码未填写的情况生成一个默认电话号码，如果未填写就留空，另外其他的填写逻辑也需要按照未填写就留空的原则来设计，记录一下。”截图路径：`C:/Users/admini/AppData/Local/Temp/codex-clipboard-b8709820-5855-471c-9b25-0c61170d8593.png`。

### BUG-20260613-004：设备信息空值显示为问号占位

- 反馈时间：2026-06-13
- 反馈来源：使用反馈
- 影响模块：设备信息/空值处理
- 严重程度：P1 核心流程异常
- 当前状态：已修复待验证
- 问题现象：设备信息中未填写的字段会显示为 `??`，截图中序列号、IMEI、机况等字段出现 `??` 占位。
- 复现步骤：进入存在设备信息缺失的订单详情页，查看“设备信息”区域。
- 期望结果：设备信息字段未填写时应保持为空，不生成 `??`、默认文案或其他占位假数据。
- 实际结果：未填写的设备信息被展示为 `??`。
- 影响范围：影响设备资料真实性、维修判断、后续查询筛选、报表导出和人工核对。
- 初步判断：与 `BUG-20260613-003` 属于同类空值处理问题，可能存在展示层 fallback、数据导入兜底、字段格式化函数或详情页渲染时统一用 `??` 代替空值。
- 建议修复方向：处理方式参考 `BUG-20260613-003`；所有设备信息非必填字段遵循“未填写就留空”，移除 `??` 占位逻辑；如字段确实必填，应在录入阶段校验，而不是展示阶段补造占位值。

- 修复说明：移除详情组件 `??` 和 `待补` 空值占位；设备信息、IMEI、序列号、机况等只读空值留空，表格类密集视图仍用 `-` 表示缺失。
- 验证结果：前端测试已覆盖空 IMEI 不再生成模拟值；构建通过；当前状态等待实际详情页验收。

### BUG-20260613-005：故障选择结果被固定写成屏幕总成更换

- 反馈时间：2026-06-13
- 反馈来源：使用反馈
- 影响模块：故障与维修详情
- 严重程度：P1 核心流程异常
- 当前状态：已修复待验证
- 问题现象：在“故障与维修详情”中，无论用户选择了什么故障，最终故障名称都填入“屏幕总成更换”；截图中故障名称显示为“屏幕总成更换”，并关联了 `IP13P-SCR-OLED` 等配件信息。
- 复现步骤：创建或编辑维修订单，在故障选择处选择非“屏幕总成更换”的故障项，保存后进入“故障与维修详情”查看故障名称。
- 期望结果：故障名称应与用户实际选择的故障一致；对应配件、服务费、小计等明细应根据所选故障和维修方案正确生成。
- 实际结果：无论选择何种故障，最终都被写入或展示为“屏幕总成更换”。
- 影响范围：影响维修记录真实性、报价明细、配件扣减、成本统计、客户确认和后续报表。
- 初步判断：可能存在故障选择值未传递、保存时使用固定默认值、故障到维修方案映射错误、详情页渲染固定取第一项模板，或测试数据兜底逻辑覆盖真实选择的问题。
- 建议修复方向：检查故障选择控件、提交 payload、后端保存字段、维修明细生成逻辑和详情页展示字段；确保用户选择的故障名称原样保存并展示，维修方案和配件明细按所选故障动态生成，不允许固定覆盖为“屏幕总成更换”。
- 验证要点：分别选择多种不同故障后保存，详情页故障名称与选择一致；对应 SKU、配件单价、服务费、小计按实际故障生成；编辑后再次保存不会被重置；历史订单详情不被错误统一显示为“屏幕总成更换”。
- 修复说明：新建和详情页维修明细不再使用固定“屏幕总成更换”演示项；选择 SKU 时优先保存并展示实际 `fault_name`/`item_name`，明细表按真实维修项渲染。
- 验证结果：后端测试已覆盖选择“电池老化”等非屏幕故障后不会被改成“屏幕总成更换”；当前状态等待实际流程验收。
- 备注：用户原始反馈：“故障与详情这里我无论选择了什么故障最终都都填入的屏幕总成更换，应该是逻辑设计有问题。”截图路径：`C:/Users/admini/AppData/Local/Temp/codex-clipboard-03d40582-4378-479c-9175-823efef1c772.png`。
